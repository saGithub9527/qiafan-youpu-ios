# 计划07：同日多菜、多餐补记

2026-10-04。依据设计档案 `04-计划与备菜/07-补记做菜.png` 与用户“一个日期补多个菜品和早餐/午餐/晚餐”的明确修正。对应 RAG：`plan-backfill-r1`。这里只记录本页交付，不表示成本、食材或整个计划模块已完成。

## 页面与操作

- 计划08与“我的”做菜记录的新增入口改为 `QFBackfillCookingViewController`，保留原生 push/pop、固定导航与底部保存、滚动表单。计划入口携带当前家庭范围，“我的”入口为个人范围。
- 一个实际日期，1–30道菜，每道菜独立餐次。每次展开一道菜，用“第n/m道菜”切换，避免一次生成30套材料输入框。日期不能晚于今天。
- 从已有分页菜谱目录选择，或手动填写菜名。选择菜谱后材料数量清空，必须确认实际消耗；不把标准菜谱用量自动当作已使用量。每道菜1–40项材料，材料可以从已有食材目录添加、替换、删除，单位用服务器的单位代码。
- 四列保持食材、实际用量、单位、库存单价。材料数量输入有边框；选择控件保留箭头。紧凑单位列在中文/日语/韩语显示名称，其他语言显示服务器单位符号，无障碍读出完整本地化名称。操作表锚定实际按钮。
- 缺少库存价格依据时单价及总成本明确显示待补全，沿用设计的警示色，不显示0元或猜算金额。本页没有实现库存成本计算。当前补记从当前库存扣量，历史时点库存重建与过期策略尚未完成，见后端 `docs/inventory-cost-gap-20261004.md`。

## 本地草稿、读取与写入

本地 `QFContentDraftStore` 沿用环境、账号隔离；本页键为 `backfill.<personal或householdId>.<入口日期>`。同一入口恢复上次草稿，草稿内可以修改实际日期；键保留最初入口日期，因此修改日期后仍从原入口日期恢复。后续统一草稿列表可改善跨日期查找，当前没有宣称具备该入口。

输入日期、餐次、菜名、数量、单位和切换菜品只更新本地草稿。首次读取单位；选菜、改变材料或切换当前菜时读取余额，取消过期的余额请求；输入数字不反复调用余额接口。编辑表单没有下拉刷新。读接口使用既有缓存；库存读取失败显示待核对，不当作0库存，提交结果由服务端事务决定。

保存调用 `POST /api/v1/me/cooking-records/batch`，body是 `{requestId,date,householdId?,items}`；每项 `{id,recipeId?,title,meal,currency,materials,note}`。不发送cost或plannedMealId。完整请求、UUID、顺序和语言在第一次写入前本地持久化。

| 结果 | 客户端动作 |
| --- | --- |
| 有效成功回执 | 核对requestId、total、记录ID和ACTUAL模式，清理本次草稿，调用已有缓存失效和页面更新回调，然后返回。 |
| 42201/42205/42206 | 服务端业务拒绝，本批未提交；保留每道菜草稿，解冻允许修正。 |
| 断网、超时、未知结果 | 保留原请求和原语言，页面显示重试，禁止改写已提交内容。 |
| 400/401/403/404/409/429 | 保守保留原回执；可能是未知结果后重试前的权限或限流拒绝，不能随意生成新请求绕过。冲突需先核对历史或恢复权限。 |

旧个人 `cooking-batch-<入口日期>` 草稿按实际日期导入，成功前原文件保留。成功仅移除本批记录，其他日期不动；旧草稿清理失败时保留冻结回执以便安全重试。旧批次编辑器代码保留供兼容查阅，当前两个新建入口不再使用逐条PUT提交。
