# 确认完成做菜（设计06，2026-09-30）

客户端从当餐菜品的完成操作 push 进入确认页，保留现有奶油白、橙绿、圆角卡片、固定导航/底部按钮与滚动表单。设计源是 `04-计划与备菜/06-完成做菜确认.png`，RAG `plan-complete-r1`；日期和单位使用 UIKit 原生控件，布局使用现有 SnapKit，无新增第三方依赖。

## 输入与保存

- 首次读取当前语言菜谱详情和单位字典，建议量可根据计划份数缩放；用户确认的是实际量，服务器不会再按人数乘一遍。支持选择关联食材、增减材料、改实际日期及餐次。
- `GET /me/inventory/balances` 一次读取当前最多40种食材的个人/家庭库存。余额仅作快照展示，最终以事务锁内库存为准。读取失败显示待核对，不伪造零库存；用户正在输入时不重建整张表单。
- 所有字段、材料选择与待提交状态存于按环境和账号隔离的本地草稿。选择动作不写服务端。
- 点击完成，只发一次 `PUT /me/cooking-records/{stable UUID}`，附 `plannedMealId`、`expectedPlanRevision`、实际 `materials`。成功必须确认 `inventoryMode=ACTUAL_MATERIALS`；客户端不再追加旧的 consume-plan 请求。
- 网络未知结果保留同一个UUID、原语言和不可变请求体，重试不重新生成请求编号。草稿保存失败也不能解冻已经发送的请求。
- 42205（食材/单位待确认）或42206（库存不足）明确不提交，恢复编辑。409或404先强制 GET 同一做菜记录；已存在则按服务器事实刷新，记录不存在才提示用户放弃本地未保存用量、返回最新计划。不自动换UUID重试。
- 接口成功后清除此页草稿，刷新当前计划及相关缓存。原来的通用做菜记录编辑器对 ACTUAL 材料暂时只读，旧错误草稿不能覆盖服务器材料；元数据编辑省略 expectedPlanRevision，避免误当成原确认重试。

## 2026-10-10 库存缺口补充

- 计划页每次取得选中日期的计划后，再一次读取 `/me/planned-meals/availability`。逐菜展示可确定缺少的食材名称；接口按菜品独立对比当下库存，不预留份额，多个菜共用同一食材时不能将单菜“够用”解释成整天都够用。
- 当菜谱材料尚未关联标准食材 ID，客户端在同一卡片位置明确显示“食材未关联”及名称，不能把这类材料报成“缺少”或“库存充足”。2026-10-10 对测试服中文首页第一页 20 道菜、105 条材料做只读抽查，`ingredientId` 均为空；此抽样不能外推至全库。需要通过后台编辑/导入并审核材料关联后，才能为这些菜给出可靠的自动缺口。
- 完成打卡页继续保留原有实际用量输入；在同维度单位可换算时，输入变化立即更新对应食材的库存差额标签，不重建正在输入的表单。跨维度且服务端可能有食材密度换算时，客户端不推断缺量；最终提交仍由服务端事务校验。
- 用户确认每项只记录“已使用”或“有余量”。按钮在本地草稿中切换，默认“已使用”，并随打卡请求保存；“有余量”表示已使用一部分且仍有剩余，状态不推算剩余数量。数值实际用量仍按原事务扣减。对“适量”等非数值用量，仅保存用量原文与状态，不生成数值库存流水，也不把整批库存清零。成本预览只计算数值项，非数值项不虚构价格。已发送而结果未知的草稿不允许再修改状态。
